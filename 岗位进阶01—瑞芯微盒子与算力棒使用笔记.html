01

设备分工与学习重点

盒子和算力棒分别解决什么问题？

瑞芯微盒子通常承担操作系统、网络、视频接入、业务服务和任务调度；推理可使用盒子内置的 NPU，也可能交给外接算力棒。算力棒提供专门计算能力，但仍需要主机完成供电、设备识别、数据准备、结果解析和异常恢复。

我把学习重点放在“整条链路能稳定运行”：设备识别正确、环境版本对应、模型输入一致、推理结果可信、服务能够恢复。峰值算力只是硬件指标之一，不能直接换算为现场可用路数。

环节主要职责需要核对
盒子主机采集、解码、预处理、调度、管理接口系统架构、内存、网络、磁盘与温度
内置 NPU执行受支持的推理计算芯片平台、内核驱动、Runtime 与模型
外接算力棒通过厂商接口加速推理芯片方案、供电、连接速率、驱动与 SDK

不同算力棒可能采用不同芯片和模型格式，不能把所有设备都按 RKNN 部署。以下笔记以瑞芯微平台为主，外接算力棒保留通用检查路径；实际操作必须根据设备型号选择厂商工具链。

02

部署前先记录环境基线

为什么“同一份程序”换台设备就不工作？

部署依赖的不只是应用文件，还包括 CPU 架构、系统镜像、内核、动态库、驱动、Runtime 和模型转换工具。已有周报中记录了瑞芯微盒子刷机、内核和网络依赖排查，以及嵌入式、前后端部署，这提醒我应把环境整理放在复制程序之前。

Linux Shell

# 在目标设备的 Linux Shell 中执行；均为只读检查。
uname -a
uname -m
cat /etc/os-release
ip -br address
ip route
df -h
free -h
lsusb
dmesg | tail -n 60

部分精简镜像不带 lsusb 等工具，dmesg 也可能需要相应权限。命令缺失本身不说明硬件故障；应区分“观察工具不存在”和“设备不可用”。环境档案应包含镜像来源、版本、内核、依赖清单、部署包校验值、模型版本和修改记录。

刷机前应确认板卡型号、镜像适配、配置和授权备份、网络恢复方式；刷机完成后按“系统启动→网络→驱动→服务→模型”逐层验证。生产设备不能只记录“刷机成功”，还需要确认重启后服务、地址与配置仍然正确。

03

推理工具链与版本关系

为什么模型转换成功，板端仍然可能加载失败？

模型转换负责把训练侧模型变为目标硬件能够执行的表示；Runtime 负责板端调用；内核驱动连接运行库与硬件。它们不处于同一层，转换成功只能证明转换阶段通过，不能证明目标板上的版本和算子都适配。

训练模型 → 导出 ONNX → 目标平台转换与校准 → 板端加载 ↓ 视频输入 → 解码 → 预处理 → 推理 → 后处理 → 业务结果

瑞芯微不同芯片可能对应不同代工具链，RKNN-Toolkit 与 RKNN-Toolkit2 并不互相通用。应从实际芯片出发，在官方支持列表里确认工具；再核对转换工具、Runtime、驱动和示例的版本要求，保留能跑通的组合，而不是只追求安装“最新版本”。

  1. 先运行对应平台的官方最小示例，证明基础环境可用。
  2. 再加载自己的模型，核对输入输出数量、形状、布局和类型。
  3. 最后接视频和业务后处理，每增加一层都保留日志与样本。

如果算力棒使用其他厂商 SDK，沿用同样的分层思路，但模型转换工具和 Runtime 都应切换到该厂商体系。USB 设备在系统中可见，也不等于厂商 Runtime 已能正常调用。

04

预处理、量化与结果一致性

推理没有报错，为什么框和分类结果还是不对？

最常见的偏差之一是输入契约不一致：RGB 与 BGR、NCHW 与 NHWC、缩放与 letterbox、归一化参数、数据类型。必须把训练、导出、桌面验证和板端推理放在同一份输入说明下比较，不能仅确认输入分辨率相同。

量化通过较低精度表示减少存储和计算开销，也可能引入误差。校准数据应覆盖实际光照、背景、目标尺度和困难样本。只用少量容易识别的图片完成转换，不能证明现场精度可接受。

检查点应保留的信息错误表现
颜色与布局通道顺序、张量维度、连续内存要求同一图像推理结果明显异常
尺寸与填充缩放比例、上下左右 padding坐标整体偏移或框大小不一致
数值表示dtype、均值、标准差、量化参数置信度异常或结果不稳定
后处理输出结构、阈值、NMS 与坐标映射重复框、漏框或框回不到原图

例如 letterbox 后，网络输入坐标回原图通常需要先减去相应 padding，再除以缩放比例；如果直接按图像宽高做两次独立缩放，就可能破坏原来的几何关系。回归样本应固定原图、预处理结果、模型输出和最终结果，让偏差能够定位到具体一层。

05

算力棒连接与异常排查

设备能识别却跑不稳，应按什么顺序检查？

外接设备同时依赖电气连接和软件接口。首先确认电源、线材、接口与散热，再看 USB 枚举、驱动、权限、厂商 Runtime 和示例。经过扩展坞、共享总线或长线连接时，要额外确认连接质量和带宽；不能只根据接口颜色判断实际速率。

现象优先排查验证方式
lsusb 中没有设备供电、线材、接口或设备本身更换已验证接口，观察插拔前后内核日志
可见但 SDK 打不开权限、驱动、Runtime 或进程占用运行厂商最小示例，记录完整错误码
连续运行后断开供电波动、温升、线材或链路错误对齐断开时间、温度和内核日志
推理成功但吞吐低传输、数据复制、主机预处理分别计时，比较连接速率与 CPU 使用

排错时一次只改变一个条件，并记录旧配置、新配置、现象和日志。权限问题应按设备规则解决，不宜把业务服务长期以最高权限运行当作修复。设备断连后还应验证服务是否能正确报错、释放资源和恢复，避免界面仍显示“运行中”。

06

性能测试要测完整链路

模型耗时很短，为什么业务延迟仍然很大？

单帧时延可能由解码、预处理、数据传输、推理、后处理、排队和业务输出共同组成。串行处理时，各阶段耗时可相加估算；存在流水线并行时，吞吐通常受最慢阶段和资源争用限制，不能用总耗时简单反推所有并发情况。

举一个教学例子：预处理 5 ms、传输 3 ms、推理 12 ms、后处理 4 ms，串行服务时间约为 24 ms，还没有计入排队和视频输入。这里的数字仅说明计算方法，不是本人的设备实测值，也不能据此承诺约 41 路或某个实际帧率。

  • 测试条件：设备型号、镜像、Runtime、模型、输入尺寸、视频编码、帧率和路数。
  • 核心结果：有效处理 FPS、端到端延迟、P50/P95、失败数、丢帧和排队情况。
  • 资源情况：CPU、内存、NPU、温度、磁盘与持续运行趋势。
  • 边界情况：断网、断流、重连、设备重启、算力棒断开与恢复。

先预热再统计，说明采样窗口和样本数量。不能把模型只推理一次的耗时当作持续处理能力；也不能只以“进程没有退出”认定长期运行正常，要同时看输出是否持续、队列是否堆积、资源是否漂移。

07

学习收获与部署检查单

怎样让一次部署经验变成下次可复用的方法？

我的主要认识是：嵌入式部署需要把软硬件和业务串起来。环境问题不一定通过重装解决，推理异常不一定是模型问题，性能不足也不一定来自 NPU。先保留环境基线，再从最小示例向业务逐层推进，更容易找到故障边界。

  1. 部署前：确认硬件型号、工具链、镜像和备份，准备匹配的依赖与模型。
  2. 部署中：分阶段验证系统、网络、驱动、Runtime、模型与业务服务。
  3. 部署后：验证开机启动、配置持久化、连续运行、断流恢复和日志定位。
  4. 归档：环境表、操作步骤、软件校验值、典型错误和恢复方法放在同一记录中。

后续具体设备实测可按这套检查单，补充型号、工具链版本、输入条件和测试结果，逐步形成可复用的部署与测试档案。
